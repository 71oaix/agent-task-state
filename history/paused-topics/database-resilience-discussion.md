## 用户怎样把问题一步步推向系统设计

第一轮（复制文本第2行起）用户提出：先记录任务试错中的事实，再让 Agent View 与 Human View 从中生长。这是整个讨论的起点，而非最后才附加的展示能力。相应回复讨论多个视图、后续分析以及不必因展示变化重新执行任务，同时强调事实库不等于保存所有日志。

第二轮（第256行起）用户追问是否已有工作实现这种思想。回复将状态恢复、持久运行、轨迹记录与任务知识区分，提出单纯采用事件溯源不能作为创新；应核查“发生过什么”怎样转成有证据关系的任务理解。这轮涉及 ESAA、Pi Durable、LangGraph、Temporal、ATIF、Phoenix、Letta、AMBER 等线索，相关机制与新颖性判断尚未核验。

第三轮（第638行起）才要求调查事件存储应该保存什么。第四轮（第1218行起）要求专业词补充中文解释，避免研究表达本身阻碍理解。

第五轮（第1227行起）用户把分析重点从字段转向价值：先比较每项工作解决的实际问题，在其基础上发展更综合的方式；改进要体现在整体管理和依赖机制，不能只把记录内容统一。

第六轮（第1593行起）确认完整系统应博采众长，同时精简，只取必需。第七轮（第1814行起）要求先交付六项工作的名称、问题、解决方式、贡献与缺陷，再推理它们如何形成合力，并借成熟软件工程机制提高可靠性。

完整推进顺序是：维护任务事实并派生视图 → 追问已有先例 → 调查记录对象 → 从字段比较转向价值与局限 → 精简并组合机制 → 补足可靠运行条件。Context 管理、人的展示与评估都是状态的下游用途；不能把整个方向重新收窄成摘要技巧或数据库抗故障。字段只是表达机制的工具；完整不意味着全收。

## 助手提出、用户认可方向但仍需论证的机制

对话提出把历史、Agent 判断、语义依赖、当前状态和读者视图分开；历史保留实际发生及被接受的变化，当前状态能够从记录恢复，视图按用途生成。

依赖不能只用于画图。上游条件变化应使相关结果进入待重判断状态，并支持只更新受影响部分。试错通过分支、修订和选择表达，而非线性日志；还应能区分当时已经知道的信息与后来才得到的信息。

运行边界是 Agent 提议、可靠系统控制写入；恢复历史不能重复执行真实外部动作。这些是对话中助手提出的候选机制，不因用户认可总体方向就视为已逐项批准或已证明有效。

“最小核心、丰富派生能力”是上述讨论的设计归纳，不是选定了具体基本对象、表结构或数据库。

## 对当前设计的实际影响

全文补查没有发现需要推翻 v0.2 已有机制的依据，但纠正了其推理起点：可靠性为任务事实到工作视图这条链服务，而非独立替代长程复杂工作目标。v0.2补充该说明及有条件的历史再分析能力；本次是来源纠错与设计澄清，不伪称来自新实验，也不另造一次重大设计升级。

[v0.1](design-v0.1.md)已经保存工作身份、版本和按需证据，但没有充分规定历史到现状的恢复路径，Agent 判断与观测的区别也未成为明确写入边界。

[v0.2](design-v0.2.md)因此补充可恢复历史、受控写入、可重建视图、依赖触发和历史时点，同时保留复杂任务及摘要优先的目标。该修订来自用户提供的新设计材料，未经过真实任务验证，不是实验发现。

研究选取机制时必须回答：不用它会导致什么实际失败，它能否由现有机制承担，新增维护负担是否值得。文献核验顺序与问题仍在[来源清单](../docs/research/change-graph-task-state/source-inventory.md)维护。本文保存吸取过程，设计行为只在当前设计版维护。
