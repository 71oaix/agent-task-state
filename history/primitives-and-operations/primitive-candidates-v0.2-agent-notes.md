## 版本与身份协议

工作身份跟踪可持续管理的工作单元，修订标识固定内容。调用者显式提交身份、来源修订、内容及身份延续或新建理由。新建无父版本；修订可沿同身份延续；分叉可引用已有版本建立新身份。并发修订同身份不自动成为两项新工作。

保持身份与拆出身份是管理决定，不能仅由目标文本相同或代码相似度推导。需要独立安排、暂停、验收或放弃是拆分提示；并非充分的自动判定条件。身份解释后来改变时新增有版本的映射及适用范围，不改写历史标识或把旧引用静默重定向。

整合输入须明确来源版本、取用范围、已知必要依赖、冲突及处理记录。调用者提出整合候选；版本登记检查引用存在、类型及声明完整性；选用检查配置规则、权限及未决事项的处理政策。程序只能核查已表达的依赖，不能证明不存在隐含依赖。待核查候选可先保存；是否允许选用取决于显式政策，不能把保存成功等同于兼容。

关系与工作共用不可变版本设施，但有不同类型约束。关系修订有自己的身份和修订标识，端点引用精确版本；替代关系注明作用范围及原因。配置引用关系集合的不可变入口，因此关系修订不自动传播到所有配置。历史配置仍可解析旧关系。新增独立证据不默认 supersedes 既有证据；inactive 只是配置下的派生状态。

## 初版并发协调协议

### 配置与事务边界

一份项目配置 P 固定当前采用的工作版本、关系集合、约束规则和相关安排。scope 限制本次允许修改的范围，不提供独立提交保证。所有当前配置变更竞争同一个项目配置版本；候选产物可以独立登记、并行积累。

调用者可以提交局部 delta，prepare 从明确的 base 构造完整 next_config。record 以 expected 配置版本检查并原子登记整份更新、对应决策和必须同时生成的复核义务。不能只采用 delta 的一部分；否则应创建一个新的、明确说明改变的请求。纯 prepare 不产生已经接受的决定。

登记检查：精确引用存在且类型匹配、预期版本仍为当前版本、主体有权限、必需读依赖及规则版本适用、整份新配置满足已声明的可执行约束。语义约束若没有可靠判定器，只能引用已有审查或标为待决，不能伪装成程序已证明。外部世界未报告的变化不在事务保证之内。

### 冲突规则与处理

1. expected 与当前 P 不一致时，原请求不提交。候选成果保留。
2. 使用 base、当前配置和请求 delta 做三方比较。写入同一配置位置为不同值构成直接冲突；读依赖、关系集合或规则改变使原验证失效；共享约束针对合并后的完整配置检查。
3. 对更新位置独立或相同赋值、读依赖仍适用且完整约束检查通过的请求，可按确定规则重新 prepare，以新 expected 再次登记。任何再次变化仍重新检查。不得自动合并任意自然语言结论。
4. 不能证明兼容时记录协调事项，引用双方候选及冲突前提。按已声明权限由协调 Agent、规则或人提出新候选；新的候选仍经过相同登记检查。没有政策时不临时采用最后写入获胜。
5. request_id 用于同一请求的重试去重；同键不同内容拒绝，不能把两个主体的不同决策当成重复请求。

例如共享预算只剩一单位，两个 Agent 从 P0 分别增加一单位，即使修改不同组件，也不能都接纳。第一项成为 P1 后，第二项在完整配置上重检将超额。整体配置串行接纳是避免这个漏检的初版选择，不是已经测得的性能结论。

读依赖需同时覆盖内容引用和所查询的集合或配置版本，避免只检查已返回的对象却遗漏后来新增的约束。初版以项目配置版本统一发现这类记录变化，代价是可能拒绝实际无关的并发更新。细粒度 scope 并发优化留待有证据显示其必要性后讨论。

## 适用性维护的具体展开

| 步骤 | 保存和选用 | 保证边界 |
|---|---|---|
| 原始判断 | C1：“A7 满足 R:v3”；T1 为针对 A7 的测试；L1 引用 C1、R:v3、T1 及必要前提；P1 选择这些版本 | 测试通过及结论适用范围分开记录，不从日志存在推导结论正确 |
| 新要求 | 保存 R:v4 候选，提出配置变化；依赖规则发现原判断必要前提改变，生成带触发版本及规则版本的复核义务，与 P2 一起登记 | needs_recheck 是义务或投影状态，不代表旧判断在旧条件下被证伪 |
| 范围分析 | 有明确规则证明某项前提未受影响，可记录理由免于复核；未知则保留待查 | 不能仅因两个版本文本相似就省略复核 |
| 新证据 | T2 针对 A7 和 R:v4；产生 C2 及新依据，记录复核结果并形成 P3 | 新条件下失败不删除旧条件下的成功；通过则新增支持 |

前提不是仅藏在 justification 自由文本中：已知必要前提作为精确版本端点和类型关系表达；justification 解释为何建立此关系，scope 表示适用范围，不承担万能失效标记职责。复核义务用版本化对象和关系表示，经现有登记与选用操作形成，无须新增 invalidate 原语。是否值得作为便利接口封装是后续问题。

StateMem 的方法已有 supersession 和依赖传播。本模式仅说明组合如何工作，不作为新颖性主张。

## 十项场景的近邻机制映射

这里比较已读原文的表示和规则；不是运行结果。表中“未核实”表示目前没有支持该保证的证据，不能推出方法理论上做不到。候选列同样只是设计承诺，没有实现证据。

| 工作变化 | MAGE | StateMem | ESAA | 本候选及需检验之处 |
|---|---|---|---|---|
| 1. 同一工作的持续修订 | 原始执行节点及上层摘要、维护与修订 | 新状态单元替换旧单元，保留旧记录 | 事件及任务投影、状态流转 | 稳定身份下多修订；身份规则是否比既有结构更必要未证 |
| 2. A/B/C 并行探索并保留成果 | 替代分支可保留；独立并发路线配置未核实 | 可保存多项内容；并行产物版本协议未核实 | 有多 Agent 任务认领与归属规则；路线版本模型未核实 | 候选并行保存、选择串行接纳；需检查并发成本 |
| 3. 人决定暂缓 A、优先 B，A 未被证伪 | 当前路径与分支提示可承载切换信息；非错误暂停语义需额外约定 | 来源与状态内容可记录决定；暂停与 supersession 的区分需约定 | actor、任务动作及投影可留痕；该路线决策的原生动作未核实 | 选用和证据结论分离；不能只因有 select 名字判定优越 |
| 4. 恢复 A，同时保留期间其他进展 | 分支修订及提示有关；局部恢复对全局状态的规则未核实 | 可重新记录相关状态；旧产物版本重选未核实 | 事件可恢复投影；重新选旧路线与重放不等价 | 新配置选旧 A 版本而保留其他当前项；依赖需重查 |
| 5. 只吸收 B 的一项成果 | 分支提示可提供信息；组件依赖边界未核实 | derived_from 记录依赖；产物局部整合协议未核实 | 可记录执行动作；部分成果来源和兼容性需扩展约定 | 整合为高阶过程；候选本身也未解决隐含依赖识别 |
| 6. 修正挂错的证据关系 | 摘要维护能修正内容；关系独立修订未核实 | 单元可替代、依赖有类型；关系独立版本生命周期未核实 | 追加纠正事件可表达修正；关系版本依赖事件模式 | 关系版本及集合入口；收益需与追加事件表示比较 |
| 7. 不同组件争用同一共享额度 | 项目级共享约束并发协议未核实 | 状态依赖不等于共享资源事务保证 | 有确定性校验和归属约束；任意共享约束协议未核实 | 全配置重检避免记录内写偏差；代价是较粗的串行点 |
| 8. MVP 已完成但留下技术债 | 摘要与分支提示可记未决事项 | 多个状态单元可保存完成与债务 | 可用任务、issue、hotfix 关联继续工作，不能说 done 后无法返工 | 完成一个成果不自动关闭其他义务；不是仅本候选可表示 |
| 9. 新需求使旧依据需要复查 | Maintain 有内容核查；条件版本驱动传播未核实 | 原生 supersession、依赖传播、needs_recheck | 新事件和投影可记录；该传播规则需模式或验证器支持 | 版本依赖生成复核义务；与 StateMem 重叠明确 |
| 10. Context 压缩后接续与查证 | 分层摘要、近期轨迹及兄弟分支提示直接服务该问题 | 持久状态及来源，渲染 active 状态供回答 | 事件、投影和校验支持可追溯状态 | 从配置生成视图并链接历史；尚无视图策略或收益证据 |

目前不能据此证明表达能力严格更强。任意可扩展事件或文本表示通常能编码更多内容，真正要比较的是所需额外约定、信息是否机器可定位、更新时是否强制一致，以及记录和维护成本。后续应固定相同真实过程，列出各方法的具体记录与操作；适配扩展必须单列成本，不能只给候选无限定制。
