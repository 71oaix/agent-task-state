
# 从架构假设走向可检验机制：研究计划 v0.2

状态：已归档

我们要检验的是：**复杂开发反复变更方向、积累试错并经历多次 Context 压缩后，Agent 能否根据保存的工作继续推进，并正确区分哪些成果可复用、哪些判断需要重审。**

当前推荐保留“版本化工作库、语义维护器、视图生成器”作为研究中的职责划分；当前任务状态是维护出的结果。组件数量和“工作、陈述、证据”三类对象都不冻结。架构 v0.4 保留为上一版设计，本计划吸收后续讨论，不把设计合理当成效果成立。

路线是：**相关领域广搜 → 归纳共同问题并筛选精读 → 形成语义模型与设计依据 → 用真实工作检验表示 → 最小原型检查可靠性 → 对照实验判断收益 → 收缩成论文主张。** 每一步留下可以审阅的结果，再决定下一步投入。

## 1. 从哪里吸收经验：带着问题读，而不是收集名词

先广泛收集具有问题或应用背景相关性的研究，再归纳共性、筛选精读，最后形成设计依据。下表列出的工作只是检索种子，不能充当预先锁定的精读名单，更不能据此限制设计空间。

广搜分两圈：核心圈是复杂软件开发、长程执行、多 Agent 协作、需求演化以及压缩后的工作延续；相邻圈是能直接帮助解释这些问题的版本管理、来源追踪、增量依赖、事件历史和语义建模。纯问答记忆或其他领域的图方法，只有能明确说明可迁移机制及其边界时才纳入。既搜支持我们设想的工作，也搜不用图、简单记忆有效以及方法失败的证据。

粗读先看问题、背景、方法轮廓和实验任务，回答它是否真的面对相近困难；不能只因标题包含 memory、graph 或 long-horizon 就保留。沿引用、被引和代表性系统继续扩展。随后按共同困难和处理方式归组，比较各组保存了什么、为什么保存、何时更新、拿什么证明有效，允许材料推翻我们预设的分组。

精读选择每一类的代表方法、最直接的竞争方案、重要反例和证据较强的工作。细读方法、数据结构、更新规则、实验设计、消融和失败分析，必要时追到代码与实际记录；不要求所有粗读文章都精读。停止扩展的依据是：关键问题和相反路线都已覆盖，新增检索主要重复已有类别，重要空白已明确记录。它不是穷尽性检索保证，也不按凑满篇数结束。

最终给用户的是一张解释问题与方法关系的研究地图，以及有证据支持的设计取舍。检索词、排除理由和出处细目留在 Agent 说明中。

| 我们需要解决的事 | 优先研究的来源 | 要得到的判断 |
|---|---|---|
| 同一工作被多次修改、暂停后恢复，身份和历史如何保留 | JJ 的 Change / Revision / operation log；事件溯源的事件与当前状态分离 | 工作身份、版本和发生过的操作如何区分；恢复旧路线为什么不等于回滚整个项目 |
| 一个判断由谁提出、用了什么依据、前提改变会影响哪里 | W3C PROV；Bazel Skyframe 的依赖和增量重算；Zep 的时间化事实 | 哪些关联值得显式记录；哪些变化可由程序传播，哪些必须重新语义判断 |
| 压缩后究竟保留什么，为什么这些信息足够 | MAGE、InfiAgent、StateMem；补查 Zep；用 CAT、SKILL.state 检查强对照遗漏 | 原文中的失败场景、信息选择理由、消融证据和实验代表性；已有方法到底覆盖到哪里 |
| 执行如何记录、断点如何恢复、如何独立评分 | Harbor ATIF；InterruptBench、CFRC；SWE-EVO 的环境与评分实现 | 可复用的记录格式、环境恢复和评分能力；缺失的复杂工作演化应如何补充 |

官方入口与核验范围放在[执行与证据说明](research-plan-v0.2-agent-notes.md)，不用读者逐条查证。优先读方法、具体记录、更新操作、消融和失败案例；只有摘要和排行榜不能完成这一阶段。

每项候选机制必须能回答：“它解决哪种已观察到的困难？简单办法为什么不够？现有实验支持到什么程度？”没有支持就保留为假设。不能把构建系统的确定性依赖重算直接移植为 LLM 判断的正确性保证，也不因论文使用图就断言我们需要图数据库。

**完成标志：**得到一份有取舍的机制比较，以及待检验的最小对象和操作草案。已有工作能直接解决的部分采用或适配；仍存在的缺口必须具体到某种工作变化及其后果。

## 2. 从真实工作中检验结构，不再用简单任务决定复杂系统的价值

**应用与评测优先复杂软件开发和软件演化。** 其他领域只作为可迁移机制或辅助诊断的来源，不替代主场景的有效性验证。SWE-EVO 是候选之一，继续寻找同类任务，不把一个数据集锁成唯一选择。

采用两种互补材料。第一种是公开项目的连续 issue、PR 讨论、修改、测试与后续返工，用来观察真实决策和演化；第二种是可以恢复环境并检查结果的长程开发任务，用来做执行实验。公开历史缺失的尝试和动机标为未知，不能替作者补故事。

优先审查 SWE-EVO 是否适合作为执行底座。其官方资料确实面向软件演化，但这不等于已经提供了“运行中改需求、并行探索、暂停后恢复”的完整轨迹。要检查实际实例、输入时序、测试和恢复方式之后才能选用。InterruptBench 等已有断点资源用于借鉴恢复协议；之前销量任务不承担代表性证据。

第一轮选 **3 个有充分历史证据的复杂工作过程**做设计探索，另留 **2 个未参与设计的过程**检查是否过拟合。这是控制设计工作量的起点，不是统计样本量。覆盖方向切换与恢复、需求变化与返工、并行探索与成果复用；不强求每个过程包揽所有现象。找不到公开证据时记录材料缺口，不能用编造轨迹补齐。

在每个时间点，只使用当时已有的信息，尝试完成真正的操作：登记一次探索、修订同一工作、保留未选路线、记录主体的选择、关联验证结果、变更前提、恢复旧工作。检查现有对象能否自然支持这些操作，而不是只检查字段能不能装下文字。

同一段历史分别整理为一份认真维护的普通工作文档和候选结构。若普通文档已经能可靠支持同样的接手和更新，必须把它作为强基线。结构化方案要解释额外收益，不能靠故意写差摘要获得优势。

**完成标志：**交付可点击查证的工作历史图、同一状态生成的 Agent 接手摘要，以及必须保留和可以删掉的信息。冻结候选对象后再看保留案例；若必须不断增加特例才能表示，就返回修改结构。手工检查只能支持表示可行，不能证明模型使用后更有效。

## 3. 先明确语义模型，再让 LLM 在其中工作

先维护一份共享、可版本化的语义模型，规定概念的含义、彼此关系、适用条件、允许的更新，以及证据不足时怎样表示未知。它不仅是一张字段表，也包含行为规则与正反例。词语可以有别名，但在同一模型版本和明确语境内，应映射到清楚的定义；存在多种解释时保留歧义，不强行唯一化。

例如，“负责人决定暂缓 A、优先做 B”更新的是路线安排，不推出“A 已被证伪”。“B 的一次测试失败”首先记录某个版本在某些条件下的结果；要推广为整条路线不可行，还需要额外依据。前提变化可以触发相关结论待复核，不自动把它们改成错误。

LLM 依据语义模型识别记录并提出更新，程序检查概念、版本、引用和可执行规则是否满足。模型没有表达能力或信息不足时，允许提出新概念、保留未知或等待复核，不能为了符合已有词表扭曲事实。语义模型自身修改也要版本化，旧记录和推理需能解释其使用的是哪版含义，并明确哪些需要迁移或重审。

这里的“唯一”是共同语义和明确解释范围，不意味着现实只能存在一个判断。相互冲突的主张可以并存，只要分别保留主体、前提和依据。概念与规则的一致性可由定义和程序约束加强；LLM 是否把真实事件映射正确、证据是否足以支持结论，仍需验证。

先用真实开发记录与边界案例检查语义模型能否清楚解释，再接入 LLM。额外设置“相同记录、相同 LLM，有无明确语义模型及规则校验”的对照，观察误分类、越权推导、冲突处理和最终任务效果；同时检查规则是否过窄，导致合理的新情况无法表达。不能把格式合法率当成语义正确率。

## 4. 需要实验，但先做便宜而能排错的实验

最小原型只实现：记录与版本、接受更新、维护当前状态、生成可追溯的图和 Agent 视图。先不做完整平台、插件市场或通用数据库。

先检查不需要付费模型调用的可靠性：重复写入是否产生重复效果；两个 Agent 基于同一旧版本提出更新能否暴露冲突；中断后是否能恢复已接受状态；视图能否指向生成它的状态版本；历史证据是否仍能定位。重建已经接受的状态不应重新请 LLM 推理，更不应再次执行外部操作。

然后进行小规模模型试验，分两步定位问题。先给维护器人工核对过的输入，检查它是否正确处理变化；再让系统从原始执行记录提取信息，检查提取错误和遗漏造成多少退化。前者是诊断条件，不能替代后者的端到端结果。

LLM 多次推理不要求逐字一样，要看是否一致地保留事实、识别应复核的依赖并作出可接受的更新。同时统计“一致但错误”和“输出不同但都合理”，避免把输出稳定当成可靠。

**完成标志：**基础记录与恢复检查通过；知道误差主要来自记录、语义维护还是视图生成。此时才决定值得投入哪一种机制，而不是所有功能一起上实验。

## 5. 怎么检验它确实帮助了长程任务

核心实验必须让 Agent 继续实际开发，经历多次压缩、工作变化和恢复，最后检查代码与当前需求。仅回答“之前发生什么”或完成一次接手，不足以支持我们的主张。

设置两层实验。第一层让不同方法从同一个任务断点、同一环境和相同可见历史继续，便于判断记忆机制造成的差异。第二层让方法从头运行、自己积累和维护状态，检验维护误差是否随时间累积。人为安排的需求变化须单独标注为受控干预，不冒充自然发生的开发历史。

| 比较条件 | 它帮助我们回答什么 |
|---|---|
| 持续维护的工作文档、执行清单、摘要与按需查证 | 一个认真做好的普通方案是否已经足够 |
| 内容与版本相同的工作库，使用普通检索和固定视图 | 收益是否只来自保存更多信息，而不是关系或语义维护 |
| 与场景最接近、可公平适配的公开方法 | 相比已有研究是否有新增价值；无法复现时说明适配范围 |
| 候选完整机制，以及分别关闭依赖关联、条件化失败记录或动态视图的版本 | 哪一项机制真的带来收益；避免把整套系统的改善归因于“用了图” |

不必一次跑完所有组合。先用探索集筛掉无作用的机制，再冻结主张、协议和对照，用未参与设计的任务验证。模型、工具权限、可见证据和上下文上限相同；维护和检索所用的额外模型调用计入成本。既报告统一资源约束下的质量，也报告质量与总成本的取舍。

主结果是**最终是否满足当前有效需求，并保持应有的旧功能**。用独立验收测试和需求逐项核验，不能只检查 Agent 自己生成的测试或让同一个模型给自己评分。

过程诊断关注：是否重复已经排除且前提未变的尝试；是否误把暂停当作证伪；是否沿用已过期判断；是否遗漏未完成工作；恢复后是否实际推进。前提改变后的合理重试不算重复错误。另计状态维护、视图生成、查证、失败和重试的全部耗时与调用成本。

必须放入“不应失效”的对照变化，防止系统通过把所有历史都标成待复核来获得表面安全。长程的判断依据是实际交互、压缩次数和跨阶段依赖，而不是任务描述长、修改文件多。

重复运行用于估计模型随机性；按任务或项目划分探索集与验证集，不能把同一轨迹的多个断点当成互相独立的大样本。正式样本量根据先导实验的方差、希望识别的有意义改善和预算决定，并提前冻结分析规则。

## 6. Human View 也要验证，但不与 Agent 能力混成一个分数

先检查人能否通过图准确回答：“谁决定暂缓 A？B 的失败依据是什么？A 恢复时哪些结论需要重查？执行清单还有什么没验收？”与可检索的时间线或工作文档使用相同底层材料比较，记录正确率、完成时间、查证路径和误解。

用户可以先参与形成性审阅，帮助发现明显设计问题；如果论文要声称普遍改善人类理解，还需要独立参与者、统一问题和顺序平衡。个人觉得图清楚是设计反馈，不是普遍有效性的证明。第一篇论文可以把图作为可审计入口，先不声称经过完整人因验证。

## 7. 怎样收敛，而不是一直加组件

| 检查点 | 继续的理由 | 需要收缩或转向的结果 |
|---|---|---|
| 机制调研后 | 找到现有方案未充分处理、且实际重要的工作变化 | 近邻已完整覆盖：采用它，寻找剩余问题，不重新命名已有方法 |
| 真实工作表示后 | 同一组对象和操作支持不同项目，未见案例不用大量特例 | 普通文档同样可靠，或图只改善展示：收缩对内部结构的主张 |
| 最小原型后 | 恢复可靠，语义更新的收益可与提取错误区分 | 自动维护频繁损坏状态：改为建议更新，或缩小自动推理范围 |
| 对照实验后 | 未见任务上改善最终质量或减少有害返工，收益足以覆盖维护成本 | 收益只来自更多 Token，或删去某机制并不变差：不保留它作为贡献 |

收敛的单位是“得到证据支持的机制”，不是三个组件或三类对象。允许最终论文只研究其中一个困难，例如前提变化后如何选择性重审旧结论；但现在不预先宣布这就是创新点。

下一轮优先完成第一、二阶段：**相关研究地图与精读选择、由精读形成的设计依据、可用的软件开发任务候选及环境审查、经过工作操作检验的语义模型与数据模型草案。** 此后再提交具体原型范围和实验协议。当前计划不启动付费实验，也不把样本数量、模型和评分器提前定死。
