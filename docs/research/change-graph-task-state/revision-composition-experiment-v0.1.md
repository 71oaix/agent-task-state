# 修补、适配和撤回：可以共用哪一步？

**我的建议：把“修订”保留为基本操作候选，把修补、适配、撤回写成不同的组合动作。**它们共用的部分是：以一个明确版本为起点，改变指定部分，保留其余成果，生成可追溯的新版本。不同之处在于，为什么改、怎样确定改动范围，以及用什么确认做对了。

Loader 的撤回最能说明这个区别。开发者移除了事务回滚，却保留了初始化与导出修补；随后发现消费者不兼容，又做了适配。若简单恢复整个旧版本，独立修补也会消失；若只留下最终版本，就看不出消费者为什么需要改。

下面将这段过程与另外两类工作对照。箭头表示工作步骤；其中“修订”是本轮尝试共用的一步，其他步骤的基本操作仍待归约。

| 组合动作 | 怎样走到新结果 |
|---|---|
| 修补 | 发现故障 → 判断问题 → **修订** → 检查修补效果 → 决定采用 |
| 适配 | 外部约定变化 → 判断受影响部分 → **修订** → 检查兼容性 → 决定采用 |
| 撤回 | 指定要撤掉的变化与保留成果 → 处理后续改动冲突 → **修订** → 检查结果；需要时再适配 |

**实验支持共用这一步，也暴露了它管不了什么。**从 10 段真实过程抽出的 12 个条款变化，都能用同一种修订结构保存；但这是有限的记录实验，部分一致性来自编码方式。更有分量的是反例：漏写保留项后，程序接受了一个删掉独立修补的记录；保留旧接口的错误适配，也能通过结构检查。范围是否选对、实现是否兼容，仍需要判断和证据。

Qoder 三路分别检查规则、寻找反例、尝试接手读回。读回的 36 项回答中，30 项完整，6 项把改动范围与验证范围混在了一起。因此下一版必须分别记录这两种范围。原始输入、失败轮次和逐项评分在[实验明细](revision-composition-experiment-v0.1-evidence.md)。

**接下来先固定“修订”的规则，再比较观察、判断、验证和采用。**本轮已经看到：一次修订之后可以仍然失败，也可以留下后续责任；这些变化需要各自表达。我们要继续检查它们能否共用更少的操作，再把规则放回全部 16 段过程检验。
