# 研究计划 v1.1：材料筛选、活动归纳与接手协议

先读[接手入口](HANDOFF.md)确定实际状态；[人类计划](research-plan-v1.1.md)是当前研究顺序。本轮完成资产分类和计划，没有完成新一轮检索、活动编码或真实案例映射。v0.2 接口保留待检验，不能作为开放编码的预设类别。

## 执行单元一：来源广搜与筛选

已有来源只作为种子。检索分三路，并记录实际查询、日期、纳入与排除理由：

1. 实证软件工程与活动模型。查询 developer activities、software change process、program comprehension、modern code review、requirements change、refactoring rationale、debugging process、software maintenance、release engineering、incident postmortem 与 empirical study。先查软件工程知识体系及综述的原始参考，再沿 ICSE、FSE、MSR、ESEM、TSE、EMSE 等官方论文条目追踪直接实证研究。此处是检索入口，不表示已核查某版标准或论文。
2. 公开项目的连续过程。从可定位的 Issue、PR、review thread、commit、CI、设计决策与发布记录收集连贯片段。项目类型考虑库/工具、服务/基础设施、面向用户应用；协作结构考虑单人及多人。按可观察程度选择，不按是否符合 A/B/C 选择。
3. Agent 开发记录。沿已有 SWE 系列、SCBench 及公开轨迹来源查实际输入、工具结果、修订和验证记录；任务规格、演示日志和真实轨迹分开。优先固定版本的原始资料，不以排行榜或二手介绍代替过程。

检索用公开来源，不需要新账号或密钥；遇限流保留失败，换官方公开页面或延后，不把代理服务作为默认依赖。论文逐项核验年份、venue 与类别，登记到 source-inventory.md。新增未核实线索明确标记，不复用旧文章的接收状态。

粗筛依次判断：是否涉及实际软件工作；是否包含活动或过程证据；时间、版本和来源是否可定位；是否能观察中间变化；与现有材料相比增加什么。只有方法定义而没有活动证据的论文归入机制背景，不进入活动发生频率统计。

工作量检查点：首轮尝试获得至少三类项目背景的候选池，再挑四个探索项目和两个保留项目作为初始工作批次。数量用于限制单轮投入，不是抽样充分性或频率估计依据。材料不足时记录缺口并继续定向搜索，不用低质量片段凑数。每项目先读一个连贯过程，发现跨事项依赖时向前后追踪；不得截去失败或未完成部分只保留终局。

阶段停止规则：覆盖检索方向并完成正例、反例和不同项目背景检查后，连续两轮不同来源扩展若未增加实质活动类别，可暂停广搜，留下未覆盖范围。后续任何新类别都可重新打开分类，不声称理论饱和或领域穷尽。

## 执行单元二：开放编码与活动地图

在查阅元操作候选之前，为每个片段写自然语言描述：发生什么、参与主体、触发原因（未知可留空）、涉及对象、已有信息、改变与结果、未决后果。绑定时间或版本及原文位置。说明直接观察、材料作者自述、助手推断、未知四种证据状态。

活动边界由目的和后续影响判断，不按每个工具调用或每条消息切碎。一次片段允许多类活动和交错执行；编码保留原始顺序与跨项关联。先记录原文含义再归类，候选接口名不得作为第一轮标签。工具命令、角色、产物和活动分别描述，避免把它们混成同一分类层。

归纳共同结构与必须区分的语义，记录合并或拆分类别的理由。刻意寻找容易混淆的活动对及反例，但不预先规定答案。对同一片段允许多个合理标签；在另一次独立阅读中检查含义与出处，仍有分歧则保留，不宣称单一助手复读是独立标注者一致性实验。

报告频次时给出材料分母、选样方式及可见性限制。公开讨论常遗漏口头决定与未提交尝试，不能从“没有记录”推断“没有发生”。

产出：software-development-activity-map.md，完成实际分析后创建，作为人类报告；Agent 详细编码以来源关联记录保存，不预建空报告。

## 执行单元三：记录投影与 Agent 工作投影

每类活动保留一个完整的对应过程：原始片段 → 活动解释 → 已有载体 → 需要补记的含义 → 后续消费者与用途。逐项做删除检查：少记这项信息，具体哪次继续工作会受到影响？若已有证据足以恢复，优先链接，记录查证成本，不无条件复制。

随后明确 Agent 的读取、判断、执行、登记步骤和可执行验证。多主体决定保留权限与责任，未知依赖不能自动变成已满足。摘要可按需溯源；不规定每次执行都完整重审工作文件。

形成 activity-record-agent-mapping.md；原文、活动解释与设计建议明确分层，不能把建议记录的内容写成原项目确实记录过。

## 执行单元四：候选组合、近邻与保留材料

只有前三单元完成后，才逐项使用 v0.2 或其他候选表达活动。每例列操作序列、需保持的不变量、额外约定、无法表达或歧义之处。同步表达强文档方案和已核实的近邻；近邻允许合理适配，但定制工作量与候选一样计入。

核心比较：组合覆盖、语义可区分性、额外规则、跨项目扩展成本、维护和读取负担。任意通用记录能够容纳文本不构成语义充分性；接口数量更少不自动更简单。

移除或合并操作时重跑相同映射，看是否需要新增隐藏约定。新操作只有在多种已观察活动中出现稳定职责、且现有组合造成明确歧义或成本时才考虑；不为一个故事直接添原语。

冻结分类、操作语义和评分规则后开启保留项目。必须按项目及关联历史隔离，保留组若泄露或用于修订，重新标为探索并补选。类别数、分歧、特例和更新成本只支持已观察范围；总体最小性需更严格论证，当前不承诺。

## 原型与效果验证的进入条件

原型前提交：活动覆盖及缺口、记录/Agent 映射、候选选择理由、边界规则、最小实施范围和离线验收。实现需明确批准；付费调用另行冻结任务、模型、上下文/压缩策略、预算、对照、评分与停止条件，不从本计划推导预算。

离线验证至少覆盖正常更新、旧版本、并发共享约束、重复写入、中途失败和恢复，以及证据链接。每项测试对应真实活动或明确的协议反例，不以测试数量当有效性。

模型阶段区分表示、提取、维护和视图；长程任务实际经历压缩并继续开发，用外部验收和回归验证最终成果。强文档和方法对照享有相同材料与资源，全部维护成本计入。先导只用于估计方差和排错，正式样本量及比较方法另行冻结；不能把同一项目多个断点当独立项目样本。

## 逐关交付与验收协议

本节是执行约定，不是要求人类逐字段审阅的模板。下文报告文件名均相对于 `Agent任务状态管理/docs/research/change-graph-task-state/`。只有开始实际工作或已有实质结果时才创建；现在缺少这些文件表示阶段未执行，不是已通过。

### 通用交付规则

首次开始 G1 时创建 `research-execution-ledger.md`。每次阶段尝试追加：阶段及尝试号、输入的来源/文档版本、产物路径或固定证据位置、逐项实际检查与发现、关键缺口、判定及理由、下一项明确动作。工作完成后将产物和账本保存到 Git，再在 HANDOFF.md 更新最新状态；未提交只算本地草稿，不能标为已可靠交付。提交号可在后续账本项引用，不为记录本次提交号制造自引用循环。

过程证据初次产生时保存到主工作区 `artifacts/agent-task-state/analysis/<日期>-<阶段>-<尝试号>/`，每次新建批次，记录来源文件版本/哈希和派生方法。文档内给完整的仓库根目录相对路径。公开原始来源继续按资料分类保存，不写进分析结果中冒充观察；只有本地证据的结论要标注可迁移限制及官方重取方式。

每关只能判为：

- **通过：**本关必查项目有结果；不存在足以推翻下一步输入的关键未决项。方法失败或简单对照足够也可通过，不要求候选获胜。
- **返工：**资料可取得，但解释、覆盖、规则或检查不合格。指出返回哪一项，保留旧尝试；下游受影响结论标为待重查。
- **受阻：**必要材料无法获得，或需要未取得的权限。记录已尝试的替代路径、缺失证据及继续所需条件；可做不依赖它的工作，不冒充该关通过。

非关键限制可随通过结果保留，但必须写出它禁止哪些后续主张。来源错误、编造动机、混淆任务规格与执行历史、把不确定当确定、未披露验证材料污染都是关键问题。暂定类别可以保留，不能计为已验证覆盖。阶段验收是助手的可追溯自检；没有独立复核就不称为独立审计。

### G1：来源广搜与筛选

**输入：**当前计划、现有来源元数据及检索方向。先登记既有知识暴露，已读过的项目过程不进入未见保留组。候选接口不是筛选条件。

**交付：**`activity-source-review.md`，包含查询与轮次、纳入/排除理由、来源角色、覆盖/缺口、探索与保留分组；正式来源身份继续唯一登记在 source-inventory.md。每项来源有固定 URL/版本、访问日期、材料类型、可观察过程、缺失环节和分组。保留项目只做可用性及背景元数据筛查，不提前精读决定和执行内容；误读则记录污染并换组。

**必查：**

1. 逐项打开纳入证据，确认不是只读标题或二手介绍；论文核查方法和材料范围。记录实际读到的章节，不用获取成功代替读过。
2. 为每个探索过程定位触发或起点、中间变化、结果或最后可见状态；未完成可作为结果，不能补造缺失过程。纯最终 diff、单条任务规格可纳入背景，但不能据此归纳真实决策链。
3. 覆盖表逐项检查研究计划列出的工作环节、跨环节变化及单人/多人背景；三种来源路线分别标记已观察、只有规范或任务说明、尚缺材料。不得把“有条目”当“有过程证据”。
4. 对每个缺口判断是否阻断下一步。例如只有任务规格、完全没有实际过程，则 G2 不得开始；某类发布活动缺少直接记录，可带限制继续已获证活动，但不得宣称覆盖完整开发生命周期。
5. 每轮检索在开始时写明要补的缺口、查询范围和来源类型，结束记录实际读取、排除理由、类别变化及仍缺什么。“连续两轮无新类别”只有在不同来源扩展且关键缺口已处理时才可支持暂停，不是自动通过条件。

**通过后：**将来源版本和分组交给 G2；重要缺口尚在则定向补搜。四个探索、两个保留是初始工作量建议，材料不足或明显同质时调整并说明，不能为了数量牺牲证据。

### G2：活动归纳与地图

**输入：**G1 已通过的探索过程与限制；不精读保留组，不以旧三个操作作为标签。

**交付：**`software-development-activity-map.md`，包含活动定义、纳入/排除边界、易混淆区别、衔接图与证据链接；逐片段解释保存在带版本的分析批次。图中边说明时序、触发或依赖，三者不能混用。

**必查：**对每个类别至少走一条“类别 → 片段 → 原文”的支持链；对每个探索过程再走一遍“原文 → 活动 → 地图”的反向检查。所有影响后续行动的已观察变化均须分类、标为未知或解释为何不纳入，不能悄悄丢掉。检查相近类别是否有可说明的区别，举原材料或明确标为分析构造的反例；构造反例不计观察次数。

“常见”只能依据多个独立项目的重复观察或明确范围的实证研究，并写出样本分母和限制；单例类别保留为已观察个例，规范类别保留为暂定。类别数量不是完成标准。每项从观察推广出的判断都要区分事实与解释；分歧保留可接受的替代分类。

**通过后：**冻结地图及定义的 Git 版本供 G3 使用。未分类事件可保留为非关键未知；若它改变已提出类别含义或使关键衔接无法解释，返回分类或 G1 补材料。

### G3：记录投影与 Agent 工作投影

**输入：**固定活动地图、探索过程及原始材料的时间边界。

**交付：**`activity-record-agent-mapping.md`，每类活动说明已有载体、需要补记的含义、后续使用点、证据入口和 Agent 读取/判断/执行/登记过程；包含相同材料下的普通文档表示。详细检查结果及成本计数放入分析批次。

**必查：**每个探索过程选至少一个确实依赖早先信息的后续工作点；如果该过程不能提供这种工作点，记录不适合本检查并补材料。根据当时可见记录提出推进所需的问题，例如当前要求、未完成义务、决定主体、可复用成果或应查证的依据；不要用后来的成功路线构造唯一正确行动。

先使用拟保留记录和允许访问的引用作答，列出每次补取信息及仍未知的事项，再与当时完整材料核对遗漏、失真和时间泄漏。对每项新增记录做删除检查，记录删除后哪项问题无法可靠回答、增加了多少查证，或确实没有影响；无明确用途则删除或降为可选。普通文档使用相同证据和时间边界，不能刻意写差。

必须逐一说明 Agent 工作中的判断由谁作出、工具结果证明到哪里、失败或未知如何登记、何时需相应决策者介入。不能通过全量重读替代摘要设计而不计读取成本。此检查是分析者的表示走查，不是盲测，也不是模型继续开发效果。

**通过后：**将记录需求及正反例交 G4。关键需求无法恢复或未知被误写为确定则返工；确实无法由公开材料判断的内容明确留未知，不强求猜对。

### G4：元操作组合与近邻对照

**输入：**G2/G3 固定版本；此时才精读候选定义及相关近邻。

**交付：**`operation-composition-review.md`，含活动到记录到 Agent 动作到元操作的组合图；每类活动的起始状态、操作过程、结果、额外规则及不变量；相关近邻按原生支持、需适配、尚未核实分别说明。

**必查：**逐个探索过程按记录顺序应用操作，再从结果读回 G3 的问题；额外检查相关的不同顺序、并发、中断或重复请求，不适用时说明理由。不得只看最终记录能容纳文本。逐个移除或合并候选操作，再做相同过程，记录失去的保证及替代成本；能自然组合则承认冗余，无法判断则保留假设。

比较相同内容、相同时间边界及可访问证据；近邻没有同名接口不代表没有能力。额外规则指此前定义中不存在、为处理本案例新增的语义条件或特殊处理，不按代码行数或字段数计。明确程序保证与调用者语义判断的边界，检查是否把复杂性隐含转移出去。

**通过后：**形成可检验候选及已知失败，冻结规则进入 G5；发现表示缺陷返回 G2/G3 或修订候选。结果“不支持现有候选”可以通过研究验收，不得据此直接开始原型。

### G5：保留材料与推广边界

**输入：**冻结的分类、候选、G3 问题形成规则、G4 检查方法及未精读的保留组。打开内容前在账本保存这些输入版本和待检验主张。

**交付：**`heldout-transfer-review.md`，逐项目列成功、遗漏、歧义、特例、成本及限制，保留所有选入项目，不只汇报成功项目。

**必查：**先按冻结规则执行一次，记录问题后才允许修改。计数口径固定为：需要新增定义才能表达的活动/关系、需要新增语义条件的特例、无法判断或存在多种合理解释的片段、已有定义被迫改动的次数。每项有实例，不能靠换名称减少计数。维护成本分别记录新增/修订记录项、查证次数、实际人工或工具用时；没有测量则记缺失，不填零。模型成本仅有实际调用时统计。

本阶段检查通过不设“零新增类别”作为科学真值，而要求完整执行冻结检查、解释每项差异及受影响主张。若仍需新增规则才能满足当前拟实现能力，不进入 G6，返回相应设计阶段；原保留组转探索，重验使用新材料。若差异只是已明确范围之外的活动，限定原型范围并说明它与整体研究目标的关系，不能自行删掉用户要求的能力。

### G6：最小原型准入及验收

**输入：**G5 报告及当前可执行语义。先交付 `prototype-specification.md`：实现范围、规则到测试的对应、数据与依赖、读写边界、失败恢复、验收方式及排除项。需要用户明确批准具体实施，批准前可准备方案，不写原型。

**实施后交付：**代码、`prototype-verification.md` 和可重放测试记录。正常、版本修订、共享约束并发、重复请求、中断恢复、证据定位各相关路径有断言；测试要能暴露错误，不能只检查字段存在。所有阻断性失败处理或明确撤回相应能力，不能把失败报告当成功验收。

发现规则无法实现返回 G4；只属实现缺陷修复后重验受影响路径。任何关键未通过项阻止把该能力用于效果实验。

### G7：效果实验准入及验收

**输入：**已验收原型及明确研究主张。先形成 `experiment-protocol.md`，冻结任务/项目划分、模型、上下文和压缩规则、对照、权限、评分、停止条件、样本依据、完整费用与缺失处理。分别确认研究方案、工程条件和实际调用授权；另一项目批准不继承。

**执行后交付：**`experiment-results.md` 与不可覆盖的新运行批次。逐批核对执行是否符合协议、最终成果与回归、实际压缩和继续推进、所有维护及失败重试成本、缺失及偏离。协议变更单独成版本，不按观察到的结果挑任务、补跑或合并批次。

研究验收看证据与结论是否一致，不以显著提升为通过条件。失败或无差异如实交付；只有满足结果支持范围才提出论文主张。协议未冻结或批准缺失时停在方案，不以“计划写了”代替准入。
