# 第一轮研究结论：持续开发中哪些工作判断仍然可用

> **2026-10-13 方向纠正：**下文保留首轮调研及当时的推论，但将研究收窄为“旧判断适用性”的建议，以及由此安排的局部对照顺序，已被用户否定并撤回。当前研究目标是可组合的基本对象与操作，见[主计划的研究主线修正](research-plan-v1.0.md)。文献核查事实保留，不能再把本文旧推荐作为当前任务范围。

**建议保留任务状态独立于 Context 的方向，但暂时不要把“用图保存历史”定为论文贡献。**已有工作已分别实现执行状态外置、图式记忆、失败经验复用和压缩后的任务恢复。我们更值得检验的问题是：复杂开发的条件不断变化时，怎样保存一次尝试的适用前提，让 Agent 能够正确地继续、复用或重新检查它。

这是按[研究计划 v1.0](research-plan-v1.0.md)执行后的第一轮判断，不是方法定稿或实验结果。下面解释已有覆盖、剩余困难和最小验证。检索、固定版本、阅读深度与待核实项集中放在[证据说明](research-round-1-evidence.md)及[来源清单](source-inventory.md)，无需先读它们才能理解本文。

## 1. 已有研究解决了哪些问题

广搜后，可以把相关工作按它们真正解决的困难分成几条线，而不是按“是否用了图”分类。

**第一条线是工作中断后还能继续。**ESAA 把 Agent 提议、任务流转和执行结果保存为事件，再由程序检查并维护当前工作状态。它与我们“工作库、语义维护、视图”的设想有明显重叠：LLM 提出变更，程序约束保存，Agent 读取精简状态。我们应该吸收这种职责分离，而不能把外部状态库或程序检查说成新发明。其论文给出的主要是可行性案例；诊所案例结束时还有未完成任务，也没有对照实验说明收益由哪部分机制带来。[ESAA，2026，发表 venue 待核实，§3 至§7](https://arxiv.org/html/2602.23193v1)。

**第二条线是把过去的尝试变成可复用经验。**Reflexion 保存语言反馈，ExpeL 提炼跨任务经验；Experience Memory Graph 对失败与成功轨迹进行结构比较，再生成纠错提示。它们让我们看到：值得保存的可能不是每一步工具日志，而是导致错误的条件、行动及修正依据。但“过去失败”不等于“当前仍不可行”。EMG 的主要场景是交互环境，且需要成功轨迹提供参照，不能直接证明它适用于不断改变要求的软件开发。[Reflexion，NeurIPS 2023 主会](https://proceedings.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html)、[ExpeL，AAAI 2024 主会技术轨道](https://ojs.aaai.org/index.php/AAAI/article/view/29936)、[EMG，2026，venue 待核实，所读 v1](https://arxiv.org/html/2607.13884v1)。

**第三条线是有限 Context 下选择什么信息。**此前核查的 MAGE、Context as a Tool 与本轮的 SWE-MeM 都涉及压缩、保留或取回信息。SWE-ContextBench 则给出了一个有用对照：提供历史经验并不自动提高成功率，选择合适的经验、组织成合适的摘要才可能有帮助。其 oracle 条件由实验知道哪些经验相关，不能直接当作部署时已经解决了检索问题。SWE-MeM 的效果又涉及训练改变，不能全部归因于存储结构。[SWE-ContextBench，2026，venue 待核实，§2 至§3](https://arxiv.org/html/2602.08316v1)、[SWE-MeM，2026，venue 待核实，§3 至§4](https://arxiv.org/html/2606.28434v1)。

**第四条线是前提变化后，哪些结论要重新考虑。**这并非 LLM 时代才出现的问题。Doyle 的 Truth Maintenance System 已讨论依据、假设和信念修订；StateMem、时序记忆也关注旧事实的失效。我们应先学习这类语义与依赖维护经验，再决定让 LLM 推理什么。程序可以保证版本存在、引用完整和状态转换合法；它无法仅凭这些保证工程判断是真的。TMS 本轮核实到期刊身份及摘要，全文机制还需精读，不能提前把它当成可直接移植的方案。[Doyle，Artificial Intelligence 期刊，1979](https://www.sciencedirect.com/science/article/pii/0004370279900080)。

多 Agent 协作、执行追踪和来源标准也进入了扫描范围。MetaGPT、ChatDev 等提供组织和交接经验，来源追踪提供查证入口；它们不会自动解决旧工程判断的当前适用性。具体取舍见证据说明。

## 2. 已经有合适的复杂任务，不必从简单例子起步

本轮最重要的任务发现是 **SWE-Milestone**，早期版本名为 EvoClaw。它从真实仓库开发历史重建阶段及依赖，让 Agent 在自己持续修改的项目上连续推进。论文还记录上下文压缩、重新探索与错误传播。已经核实其发表于 **ICML 2026 主会**；详细机制以本轮所读 arXiv v4 为准，不能把所有 v4 内容未经逐项对照就归给正式论文版。[正式发表页](https://proceedings.mlr.press/v306/deng26d.html)、[v4 正文，§3 至§5](https://arxiv.org/html/2603.13428v4)。

不过，功能阶段之间的依赖图不等于方案取舍历史。它主要重建已完成的开发路径，未必留下曾经并行探索、后来搁置的方案。它为我们提供复杂项目和连续执行的基础，不能直接承担所有研究问题。

另外两类任务各有用途：

| 任务 | 它迫使 Agent 面对什么 | 与我们场景的差别 |
|---|---|---|
| SWE-Milestone | 持续修改真实项目，后续开发承受自身早期错误；会话持续，实际发生压缩 | 不是完整的人类方案讨论史，未必有暂停后恢复的替代路线 |
| SlopCodeBench | 分阶段提出新要求，旧代码继续使用，早期设计影响后续扩展 | 论文每阶段开新会话，不是原生的同会话反复压缩实验；任务是编写的演化规格 |
| SWE-Chain | 连续版本升级与回归维护，代码跨阶段延续 | 同样每阶段开新会话；需求依据发布说明及目标版本差异生成 |

表中协议来自[SCBench v2，§2](https://arxiv.org/html/2603.24755v2)、[SWE-Chain v1，§2 至§3](https://arxiv.org/html/2605.14415v1)及 SWE-Milestone v4。SCBench 与 SWE-Chain 均为 2026 年工作，正式 venue 待核实。SWE-CI、SWE-EVO 作为补充候选保留，不再简单等同于“长程压缩任务”。

**推荐先审查 SWE-Milestone 的公开执行记录，再用 SCBench 的 code_search 做工作表示的离线检验。**后者逐步从文本正则搜索增加多语言及结构匹配，确实可能暴露早期设计的适用边界。这里还没有观察到特定 Agent 失败，不能把“后来增加结构匹配”写成“所有正则实现必然失败”。

## 3. 我们要研究的困难可以更准确地表述

你提出的 A、B、C 并行探索和暂停后恢复，关键不只是记得做过什么，还要分清三件事：

- **发生了什么**：谁提出、谁决定、哪些代码和测试结果属于这次尝试。
- **当时为什么这样判断**：依据哪个需求、哪个环境、哪个验证结果；是性能不足、暂时优先级低，还是尚未完成验证。
- **现在还能用什么**：条件变了以后，旧成果可以直接复用、局部复查，还是必须重新尝试。

这解释了为什么“失败经验”应保留适用条件，为什么暂停不能被写成证伪，也解释了版本管理对推理结果的意义。记录过去的事件，与维护当前仍有效的结论，是相关但不同的工作。

我们暂时提出的研究问题是：**相比维护良好的普通任务文档，显式记录工程判断的前提与证据版本，能否帮助 Agent 在长期开发中更准确地复用旧工作，并减少不必要的重新探索？**

这个问题允许最终不用图，也允许图只服务人类查阅。要先证明缺失关系会造成具体错误，再讨论图结构或视图算法的增量。它也没有断言现有研究完全没做过；ESAA、MAGE、StateMem 和 TMS 仍是必须继续比较的近邻。

## 4. 目前不能把哪些现象归因于记忆

SWE-Milestone 的分析显示后期返工增加，并观察到压缩后阅读和搜索上升。但它也指出成熟框架能够控制 Context 的增长。**这支持研究恢复成本，不支持“压缩必然使任务失控”。**其失败还涉及错误实现、架构边界、缺少验证与早期缺陷传播；论文中的行为关联和 LLM 原因分类不是记忆机制的因果消融。[SWE-Milestone v4，§5.5 至§5.6、附录 C](https://arxiv.org/html/2603.13428v4)。

同样，多保存文件不保证效果更好。Evaluating AGENTS.md 的实验发现，额外说明会增加成本，收益并不稳定。它评测的是仓库说明对问题修复的影响，不能推翻我们的任务状态方向，但要求我们使用有维护质量的文档作为强对照，并把读取成本算进去。[2026 年 ICLR MemAgents Workshop 身份证据](https://www.sri.inf.ethz.ch/publications/gloaguen2026agentsmd)、[所读 arXiv v2 正文](https://arxiv.org/html/2602.11988v2)。

摘要应能溯源；是否回查依据，要由当前问题触发。实验中不能规定每次恢复都把全部工作文件再读一遍，否则我们测到的只是不同的信息量和读取费用。

## 5. 下一步做一个能推翻设计的离线验证

先不搭数据库，也不花钱跑模型。下一步交付一条来自公开开发任务的可核验工作片段，及两种保持相同信息的表示。

**先确认材料确实存在。**检查 SWE-Milestone 公开轨迹是否包含任务版本、工作区变化、工具结果和压缩位置，能否合法取得足够证据。若只能取得作者重建的任务规格，就明确它缺少实际尝试历史，不补写“Agent 曾经放弃了某路线”。同时取 code_search 连续阶段规格，核实完整依赖、评分接口与资源要求。

**再比较表示是否真有帮助。**一份是维护良好的任务文档：当前目标、已做尝试、判断依据、未完成清单和可查证链接；另一份把同样信息显式连到前提、版本和受影响判断。两份都不能使用后续尚不可见的答案。不是拿差摘要与精心设计的图比较。

**检验接手者能否回答具体问题。**当前要求是什么？某方案为什么暂停？旧测试到底验证了哪个版本？新要求影响了哪些判断？恢复旧工作前需要查哪一小块证据？答案允许“材料不足”和多个合理方案。没有公开证据的问题标为覆盖缺口；人为加入的需求或决策事件只能作为另外标明的压力测试。

如果普通文档已经清楚表达且容易更新，就先简化设计。只有出现反复丢失的依赖、更新难以维护或查证成本明显增加，才提出最小语义模型。该模型先约定词义、关系与更新规则，再接入 LLM；合法一致与真实正确分别检验。

离线验证只能证明表示足够与操作可行。它不能证明 Agent 任务完成率提高。此后才冻结一个小原型的端到端实验：使用同模型、同初始材料、同任务和预算，比较强文档对照与候选机制，保留原生压缩并记录实际压缩位置；评分同时看功能与回归、旧判断误用、遗漏工作、重复探索和全部维护费用。去掉版本依赖、去掉选择策略等消融，应在候选机制确实需要它们之后安排。

## 6. 这一轮收敛到哪里

已有机制表明，持久化、图、摘要和反馈各自都不是足够的新意。已有复杂开发任务也足以避免从销量修改那类简单任务开始。接下来最有价值的是查清：**真实连续开发中，是否存在因为旧判断适用条件没有被保存或更新而导致的接续错误；普通文档能否解决，额外机制值得付出多少成本。**

本轮完成了相关广搜、重点方法和实验章节核查、公开仓库固定版本的静态协议检查。未运行任务环境，未完整审计评分器，未读取完整实际轨迹，未执行模型实验。三组件和数据对象保持候选状态；设计 v0.4 保留，不因这轮研究自动变成已验证架构。
