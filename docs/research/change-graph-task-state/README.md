## 研究主张如何逐步成立

设计动机是：完整工作状态可以长期保存，但 Agent 每次行动只能看到其中一部分。真正值得研究的候选问题是：**怎样根据当前行动，选取足够且可信的状态与历史证据，并控制维护和读取这些信息的总成本？**

“持久化”“图结构”“人机共享状态”是设计选择。只有证明它们解决了具体困难，或揭示其适用边界，才能支持论文贡献。跨 Context 或跨模型接手是状态独立性的验证场景；持续执行时的信息选择同样属于本项目关注范围。

### 候选问题与可推翻假设

以下都是待检验的研究建议；排序表示当前分析优先级，不代表冻结题目。

| 候选问题 | 候选解释与机制 | 什么结果会削弱或推翻它 |
|---|---|---|
| A：哪些历史失败应进入当前 View？ | 以当前目标、方案依赖、失败原因及其有效条件选取相关 Change，可能减少重走已排除的路线 | 相同状态下，固定模板或普通检索同样有效；历史失败只增加干扰；条件变化后旧失败误导选择 |
| B：怎样保留当前有效意图，而不会沿用旧约束？ | 意图修订、决策依据及证据版本显式关联，可能减少完成测试却违反当前用户要求的情况 | 简单的当前约束表即可解决；版本关系没有额外收益；误提取或误更新反而造成偏离 |
| C：怎样判断 View 已足够支持下一步？ | 根据未决问题与证据缺口补充信息，可能比固定长度摘要更有效 | 无法可靠识别缺口；取回和反复生成的成本抵消收益；效果完全来自更多 Token |

优先研究 A 与 C 的联系：先明确“下一步需要什么证据”，再判断 Change Graph 是否提供普通检索不容易获得的关系。B 暂作为有效约束与任务质量维度保留，不把全部问题同时做成一篇论文。

### 候选论文贡献的三个出口

1. **方法论文：** 提出可复现的 View 选择方法，在公平对照下获得收益，解释收益来自哪些信息或关系。
2. **实证研究：** 若简单方案已经足够，系统说明何时历史、图关系、动态选择有用或有害，形成可复用的适用边界。
3. **评测研究：** 若现有任务无法区分意图偏离、重复探索或过期证据，研究可靠测量这些现象的任务与评分方式。不能仅因现有数据难用就宣称需要新 benchmark。

三者暂不选定。先检查近邻覆盖和具体失败场景，再决定投入路线。

## 最小区分性对照：先分清收益来自哪里

未来协议至少要分开回答“外部状态是否有用”和“动态视图是否有用”。候选对照为：

| 对照 | 用途 |
|---|---|
| 传统历史与摘要 | 建立不依赖新状态系统的参考 |
| 同一份结构化状态 + 固定 View | 检查持久化状态自身的作用 |
| 同一份状态 + 普通检索 | 检查收益是否普通相关性检索就能获得 |
| 同一份状态 + 候选动态 View | 检查行动相关的信息选择是否提供额外收益 |
| 动态 View 去掉图关系 | 检查 Change Graph 是否必要，而不是名称或数据组织差异 |

选择策略的对照应尽量共享同一状态及证据，明确相同的预算边界。先用手工、证据可核对的状态隔离 View 方法；之后再评价自动状态提取和维护误差。人工状态结果不能直接当作端到端系统效果。

候选指标包括任务完成质量、当前意图满足、重复无效尝试、过期证据使用，以及整个过程的模型输入输出、状态维护和取回成本。费用、缓存收益需有对应 provider 证据；不能只比较最后一轮 View 长度。人类理解收益若成为论文主张，需要独立的人类评估。

模型、任务集、预算、样本数、触发时机和统计方法均未冻结。本节是协议设计检查表，不是可以直接执行的实验。

## 下一步怎么推进

| 顺序 | 要回答的问题 | 产物与退出条件 |
|---|---|---|
| 1：核验直接近邻 | 现有工作已经如何表示状态、生成 Context、保存失败与约束？ | 逐篇官方证据及覆盖矩阵；若已有相同机制，调整候选贡献 |
| 2：构造可追溯实例 | 某个真实任务的哪一步需要现状以外的历史证据？ | 经范围确认的手工 Change Graph、Task State 与两种 View；若普通状态表足够，简化表示 |
| 3：形成问题卡 | 我们究竟要改变什么，为什么可能有效？ | 一项主要问题、机制、对照、推翻条件及投入建议，交用户判断 |
| 4：最小研究验证 | 可区分的收益能否出现，成本是否可接受？ | 经批准的协议和最小结果；失败也保存，不因结果不理想补跑 |
| 5：扩大与论文写作 | 结果是否稳健、可解释、可复现？ | 消融、适用边界、局限及论文主张；依据结果决定投稿定位 |

不把完整数据库、插件框架或 Human View 产品化作为问题发现的前置投入。先用一个实例和明确对照检验必要性。
