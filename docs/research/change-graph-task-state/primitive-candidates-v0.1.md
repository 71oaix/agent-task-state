# 工作管理的元操作候选 v0.1：版本、依据与选用怎样组合

**目前最值得推敲的组合是：生成工作版本、建立有含义的关系、改变当前选用。**创建、继续修改、分出路线和吸收成果，有可能归到同一种版本生成操作；暂停、恢复、交接和带着技术债继续，可以由这几个操作组合。下面给出推导与另两条可选路线，不把三个当作已证明的最小数量。

这是一份有来源依据的候选设计。研究目标仍是用小而清楚的核心支撑复杂工作，不缩成某项记忆指标。所谓“最小”需要同时考虑操作定义、数据含义和组合规则，不能靠把所有复杂性藏进一个万能写入函数来实现。

## 1. 找到的三条路径

| 核心从哪里出发 | 可以怎样组织操作 | 能自然长出什么 | 单独使用的不足 |
|---|---|---|---|
| 事件历史 | 追加已发生的事件；按规则重建状态；查询 | 审计、恢复、追踪谁做了什么 | “追加”很小，但暂停、分叉、复用等含义仍要另行设计；容易把复杂性全部搬到事件类型和解释器 |
| 工作版本 | 生成新版本；保留来源与关联；选用一组版本 | 修订、分叉、汇合、切换、保留旧成果 | 来源关系本身不能说明推理为何成立，也不能从版本新旧判断哪个方案更好 |
| 假设与推导 | 建立节点；建立假设；给节点增加推导依据 | 多种假设并存、判断在什么条件下可用、记录冲突 | 不能直接代替工作产物、执行清单、负责人安排及真实执行管理 |

第一条来自事件溯源的机制启发；第二条综合 JJ 与版本化数据库，表中操作是我们的归纳，不是它们共同提供的一套现成 API；第三条则对应 ATMS 论文明确给出的基本操作。[官方事件溯源文档](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)、[JJ 固定版本术语](https://github.com/jj-vcs/jj/blob/02afa7cab7ab706ec05fc9e8aab7b4ff9a3cd11a/docs/glossary.md)、[ATMS 原文 §4.6](https://dekleer.org/Publications/An%20Assumption-Based%20TMS.pdf)。来源版本与阅读范围见[依据说明](primitive-candidates-v0.1-agent-notes.md)。

ATMS 是这轮最直接的启发。它让同一个结论关联多组可支持它的假设，切换假设时无需抹掉其他方向。其三种操作及组合性质是原论文的主张；它对逻辑依据的保证依赖输入规则，并不证明 LLM 提供的工程判断正确。论文中的 context 是假设环境，不是模型的 Token 窗口。[Johan de Kleer，Artificial Intelligence 期刊，1986，§1、§4](https://dekleer.org/Publications/An%20Assumption-Based%20TMS.pdf)。

**我的推荐是第二条作为主干，吸收第三条的依据表达，用第一条保存实际操作历史。**这是不同职责的配合，不要求部署三套系统。

## 2. 候选组合：三个写入动作，另加读取

先区分“工作本身”和“工作某一时刻的版本”。探索 A 可以有稳定身份，A1、A2 是其不同修订；单独探索 B 有自己的身份。需求、计划、结论、产物引用和关系同样需要能定位具体版本，但不能因为都可版本化就抹掉它们的含义差别。

### 生成版本：让工作增长，已有记录保留

这个操作产生一个新的候选版本，并说明它延续或取用了哪些已有版本。不同输入形成四种用法：

| 输入与身份变化 | 工作中看到的动作 |
|---|---|
| 没有旧版本，分配新身份 | 创建一项工作 |
| 延续一个旧版本，保持工作身份 | 修订同一项工作 |
| 以已有版本为起点，分配新的工作身份 | 分出可独立推进的路线 |
| 结合多个来源，明确取用范围，保持目标身份或建立新身份 | 吸收成果或形成组合方案 |

这是可以归并的理由：四者都产生保留来源的新版本。区别放在明确的身份与来源规则中，而不是靠一段描述猜测。也可以先将这四种用法各自暴露为操作，便于使用；只要规则一致，并不因此多出四套底层机制。

“结合多个来源”不会自动完成工程合并。相同内容可以复用，矛盾可以保留为待处理项；新的整合结果由人、Agent 或确定性的工具提供，系统记录来源与结果。JJ 对版本身份和可保存冲突的处理提供了参考，但自然语言判断、目标冲突和代码冲突不共享同一个自动解决算法。[JJ 冲突文档](https://github.com/jj-vcs/jj/blob/02afa7cab7ab706ec05fc9e8aab7b4ff9a3cd11a/docs/conflicts.md)。

### 建立关系：表达来源以外的意义

新版本是从旧版本改来的，并不等于新结论由旧结论证明。因此必须能明确表达：某结论用了哪些前提和证据，某工作属于哪个目标，某个决定由谁作出，两个主张在哪个范围内冲突。

关系连接具体版本，也留下提出者和适用范围。若一个结论需要“需求 R1 和测试 T1”共同支持，就要把它们记录为一组依据；若另有独立的支持路径，再增加一组。不能把所有边都叫“相关”，也不能把一组中的“共同需要”误读成“任意一个足够”。来源描述与依据组合分别借鉴 PROV 和 ATMS，具体工作语义由我们定义。[PROV-DM，W3C Recommendation，2013，§5.2 至 §5.4](https://www.w3.org/TR/2013/REC-prov-dm-20130430/)。

关系也允许修订。发现某个依据挂错了，应留下新解释及其替代范围；旧关系保留为“当时这样判断过”，不继续充当当前依据。普通的证据支持只说明判断有依据；只有明确形式化且成立的规则才允许确定性推导。

### 改变选用：确定现在依据哪些版本推进

系统可以保存许多版本，但当前安排需要明确选用哪组需求、计划、工作版本和有效决定。这个操作记录由谁、基于什么决定采用新的组合，并留下此前组合。

选择推进 B 不会自动产生“B 技术更优”或“A 错误”的结论。新的需求被采用，也不会改写过去测试所针对的旧需求。多个并行工作可以同时被选用，不能把整个项目简化为只有一个当前分支。

“选用”的对象是一份可版本化的工作配置：哪些工作继续、哪些暂停、当前目标与约束、采用的版本和未决事项。它不是第二份随意生成的摘要。选用必须连同决定和相关关系一起保存；基于过期配置提交时须显式处理冲突，不能静默覆盖另一位 Agent 的结果。这里借鉴不可变状态与事务检查，不等于选定 Datomic 为实现数据库。[Datomic 事务模型](https://docs.datomic.com/transactions/model.html)、[并发值检查](https://docs.datomic.com/transactions/transaction-functions.html#dbcas)。

读取是另一个必要接口：读取指定状态、沿关系查证、比较版本，再组织成人类或 Agent 的视图。把它列在写入动作之外只是区分职责，不把系统宣称为只有三个接口。摘要策略不应私自改变被选用的工作判断；若摘要形成了新的判断，应作为候选版本重新记录。

## 3. 这些动作怎样组合成我们已经需要的能力

| 需要的能力 | 用候选操作怎样表达 |
|---|---|
| A、B、C 并行探索 | 从共同基础生成三个独立工作身份，各自修订；分别选入三个执行者的工作配置 |
| 负责人要求暂停 A、优先 B | 生成新的安排与决定，关联主体和依据，改变选用；保留 A 的版本、清单和成果 |
| B 有一部分失败，另一部分仍有用 | 记录具体测试与条件，关联被否定的判断；成果按自己的版本保留，不整条路线一并判废 |
| 回到 A，并使用 B 的某项成果 | 以 A 的旧版本和 B 的指定成果生成 A 的新版本；补充来源与适用判断，再选用新组合 |
| 同一项工作被两个 Agent 同时修改 | 同一工作身份下保存两个候选修订；明确比较或整合，再决定选用，不能以后写覆盖先写 |
| 先交付 MVP、保留技术债 | 记录已满足的验收与未清偿义务，关联具体工作；选择暂时接受的交付范围，之后修订继续还债 |
| 中途增加需求，搁置部分工作 | 生成需求和安排的新版本，关联影响范围并改变选用；原工作仍可查询，保留重新考虑的条件 |
| Context 压缩后继续 | 读取当前选用及其必要关系；未决问题与证据入口按需进入工作视图 |
| 人类看历史图、点开证据和清单 | 从版本演化、关系及选用历史生成投影；详情定位当时版本和实际主体 |

这是对用户已提出工作行为的设计推演，不是合成实验结果，也不是某个公开 Agent 的真实轨迹。表中“暂停”表达安排；若要停止正在运行的工具或进程，还需要执行层提供取消、确认与执行结果记录。语义工作库不自动成为操作系统或部署执行器。

把你的切换例子展开，关键变化是：

```text
A1 → A2 ──────────────→ A3（继续 A，取用 B 的部分成果）
B1 → B2 → B3 ──成果来源──↗
C1 → C2（仍保存，未选用）

当前安排：A 优先 → B 优先、A 暂停 → A3 优先
决策依据：每次安排变化各自关联主体、理由和当时版本
```

上面一层是工作如何演化，下面一层是当时怎样安排。切换安排不用删掉任何路线，也不用退回整个项目旧状态。

## 4. 为什么暂时保留这三个区别

删掉版本生成，持续修改只能覆盖已有内容，无法准确谈论旧测试和旧计划。删掉有语义的关系，剩下的版本只能说明先后与来源，无法解释依据、责任和适用范围。删掉当前选用，库里可以堆满互相矛盾的候选，却无法清楚回答此刻采用什么。

这解释了三类语义为什么值得区分，**没有证明三个函数不可再合并**。关系本身若建模为版本对象，“建立关系”可以实现成“生成关系版本”；当前选用也可以存成数据。这样可以做成“构造变更 + 原子登记”的更小写入接口，读取另外提供。

原子登记只是把一组变化完整保存到工作库，并不自动选用其中的方案。登记三位 Agent 的候选结果时，当前安排完全可以保持不变；采用方案必须在这组变化中明确表达。

更小接口是否更好，要看它是否仍有公开、稳定、可检查的规则。如果只是允许任意改写整个状态，三个名字压成一个也没有获得更好的抽象。当前有两种值得保留的接口选择：

- **语义显式版：生成版本、建立关系、改变选用，另加读取。**容易理解和检查，适合作为我们下一轮讨论的主方案。
- **事务统一版：构造变更、原子登记，另加读取。**底层更集中，但必须用类型和规则明确表达前者的全部语义；不能靠 LLM 自行遵守隐含约定。

创建、修订、分叉、整合不必立即决定暴露为一个还是四个命令。先检验它们是否确实能共用身份、来源和版本规则。核心小与调用方便可以同时成立。

## 5. 候选还剩哪些真正影响设计的问题

第一，工作身份的边界。A 的原型重构成另一套实现时仍是 A，还是成为 D，要用多个真实过程检查，不能只靠 Agent 随意取名。

第二，组合的范围。吸收 B 的成果不能自动继承 B 的所有假设、评价和安排；需要能选择成果并保留其必要依赖。能否用关系规则自然表达，决定“整合”能否归入版本生成。

第三，语义冲突。需要同时允许“来源真实但解释有争议”“结论条件不足”“两条规则不能一起采用”。LLM 可以提出关系和整合建议；确定性部分负责版本与规则检查，已经接受的解释要被保存，恢复时不重新随机生成一遍权威状态。

本轮的推荐可以具体落到一件事上：**保留上述两种接口候选，以同一套版本、关系和选用语义继续推敲。**接下来查前人操作的边界并尝试删减，检查复杂工作中是否被迫添加专用例外。尚未宣称表达完备、形式最小、实现可用或论文贡献成立。
