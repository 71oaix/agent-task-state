# Change Graph 任务状态直接近邻核验

## 判断

当前设计的大部分基础机制已有直接先例。不能把“状态独立于 Context”“执行图或树”“保留失败分支”“有效状态替换旧状态”单独包装为新贡献。值得继续检查的是：当既有状态大于工作预算、部分证据因意图或环境变化失效时，如何生成支持下一步行动的视图，决定复用、取回与重新验证，而不是只解决记忆问答。

这只是候选问题，并非已证明的空白。下面是限定于所核验版本与章节的覆盖判断；没有对整个领域完成穷尽性检索。来源身份、venue、日期与阅读深度统一见[来源清单](source-inventory.md#2026-10-09-首轮核验记录)，本报告不登记另一套发表状态。所有工作均未经本项目复现。

## 机制覆盖与对我们意味着什么

| 近邻 | 已核对的机制位置 | 覆盖的原始想法 | 仍需区分的问题 |
|---|---|---|---|
| InfiAgent | §3.2–3.3、§4.1：工作区文件是持久状态；固定 schema 的 thinking record 包含任务待办、相关文件、carry-over 与后续工具步骤，再与近期动作组合 | 外部任务状态、由状态重建有界 Context、失败与规则持续保留、恢复 | 文件状态不是我们的新增点；其固定构建接口可作为视图对照，实际适配与成本要审代码 |
| MAGE | §3.2–3.3：双层执行树、当前路径摘要与近期原始轨迹、兄弟分支提示；Maintain 校验摘要，Revise 回到边界另开分支 | 图或树表示、失败保存、从有效路径生成 Context、压缩与修订 | 必须与其路径及提示选择直接比较；不能把失败提示说成它没有。其 LLM 校验不等于外部工具证明 |
| Context as a Tool（CAT） | §2.1–2.3：固定系统与关键用户意图、历史摘要、近期 k 步；主动调用 Context 管理工具 | 有界视图、意图锚点、动态压缩与行动相关摘要 | 主动 Context 管理已经存在；意图修订与证据有效条件不是该核验章节的主要评估，不能推断完全不支持 |
| SKILL.state | §3.1–3.2：领域级 schema、不可变技能规格、当前结构状态与最新观察；验证更新，丢弃中间推理 | 显式现状、Context 不随历史增长、状态更新 | 强简单基线，CTF schema 本身已有 tested_hypotheses；不能弱化为只保存成功现状。预算匹配也已有，预算本身不新 |
| StateMem | §5.1–5.3：来源、hard/soft 优先级、依赖关系、superseded 与 needs_recheck；依赖变动传播，渲染有效状态 | 意图与事实修订、来源追踪、派生证据失效、待重算标记 | “版本变化使依赖证据失效”已有；候选差异只能是有界在线行动视图及重验证决策，并须与同一状态上的强 StateMem 式构建比较 |
| CFRC / Do Not Restart | §3.1–3.5：冻结残余合同、保留已接受选择和实际效果、关闭证据关联的后续图、以实时 receipts 验证完成 | 接手时的承诺、剩余工作、证据与完成分离 | 把“接手要遵守意图并保留进展”说成新点不成立；候选视图方法应与此治理层兼容，不能拿不检查完整义务的缩短版冒充 CFRC |
| State-Aware Runtime | v4 官方摘要及版本说明：canonical state、bounded view、验证与事务、恢复、immutable pre-proposal reference | 整体概念架构大范围重叠 | 这里只核验元数据/摘要/版本说明，未全文审协议；概念先例成立，不能据此声称已有经过 benchmark 验证的完整系统 |

核验后的立场：Change Graph 暂保留为可追溯的数据表示与候选信息来源，不提前要求最终算法必须采用图。若状态表或普通检索已足够，应该保留这一发现。

## 你记得的断点任务集

| 资源 | 已确认的用途 | 可用资产与缺口 | 本项目建议 |
|---|---|---|---|
| ContinuityBench：Aryan Gulati 的 Interrupted State 论文 | 给现有 step-based benchmark 加中断与接手协议；固定任务、中断位置和环境状态，比较 h0/h1/h2 | 官方 PDF 索引可读协议片段；网页与 PDF 下载被验证页面/403 阻断，未核实代码、已发布 checkpoint 包或具体公开轨迹 | 可复用评估思想；目前不能当作已获得的断点数据包 |
| InterruptBench：HenryPengZou 仓库 | 初始意图 + 追加/修订/撤回；动作前缀回放至中断点，注入更新并继续 | 固定提交已核实任务 JSON、raw updates、run.py、evaluator、多轮说明；真实前缀需保存轨迹，网站环境与状态需重放校验 | 本轮手工实例选 task 0；可作意图修订候选评测。不是现成文件系统/浏览器完整 snapshot 包 |
| StateMemBench | 当前状态与旧状态问答评测，包含不应更新的 anti-trap 对照 | 原文方法与构建说明可读；本轮未定位/验证数据包与代码 | 作为状态正确性辅助评估线索，不替代在线工具行动评估 |

同名排除：多供应商路由的 ContinuityBench（arXiv:2607.15899）及其他同名 GitHub 项目不是本轮引用的恢复论文。不能将它们的仓库当作 Gulati 论文代码。

ContinuityBench 的 h1 是 structured summary，h2 增加准确动作历史；它已经研究“更多历史不一定更好”。因此动态 View 必须对照它的结构摘要，而不是只对照空 Context。

InterruptBench 的多轮文档明确：通过 Stage 0/1/2 的多次 run + replay 链接更新，run.py 本身一次处理一个 interrupt；不能把文档名称解读为一个运行里已实现任意次数原生中断。

## 候选空间与否决条件

候选：**当前有效状态无法整体装入预算时，行动所需证据如何被选取、复用或重新验证？**

需要同时考虑：当前意图、下一步义务、依赖变化、证据作用范围、已实现环境效果和取证代价。这些元素分别已有先例；可能的贡献在于一个可区分的在线选择策略或适用条件发现，不能来自概念拼装。

与[手工示例](traceable-example.md)的关键衔接是：修改数量可以保留同月完整排序，修改月份需要新证据；导航进度可以保留。这个小任务用普通状态表就能解释，因此它是“不要过度设计”的校准例，不是图方法胜出的证据。

下一关：先在公开任务中找到真实、足以超过简单状态表/固定视图能力的前缀，冻结原始证据与环境状态；没有这种实例就不进入大系统实现。问题与公平对照具体见[研究问题卡](problem-card.md)。
