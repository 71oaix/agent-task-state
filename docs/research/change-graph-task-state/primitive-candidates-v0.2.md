# 工作管理元操作候选 v0.2：身份、关系与选用的责任边界

**2026-10-15 定位：**本版保留为待检验候选。当前先按[研究计划 v1.1](research-plan-v1.1.md)调查真实开发活动，不以这三个操作作为活动分类框架。

本版吸收用户对[v0.1](primitive-candidates-v0.1.md)的审阅，继续保留“生成版本、建立关系、改变选用”的语义接口，以及统一的原子登记底层。**主要修正是明确每一步由谁判断、核心保证到哪里，并把复杂整合列为上层组合过程。**还没有证明这些操作最小或完备。

研究目标始终是用可组合的基本操作管理复杂工作。旧判断适用性是其中一个检验模式，和并行探索、暂停恢复、部分复用、技术债、需求演化、Context 接续并列。首轮报告中将它作为整个研究主线的推荐已经撤回。

## 1. 工作身份：表达持续管理的对象，不能由改动大小决定

**由调用者明确声明是在继续已有工作，还是建立可独立取舍的新工作。**调用者可以是已有权限内的 Agent，不需要每次交给用户决定。程序检查声明是否合规、是否引用了正确版本，并保存声明与理由；它不根据修改行数自动判断“还是不是同一件事”。

暂用下面的规则：

- 继续同一项受跟踪的工作，即使重写实现、更新需求或换一套测试，也可以保持身份，产生新修订。
- 需要独立推进、暂停、验收或放弃的另一项工作，分配新身份，并保留其起点或来源。
- 同一工作被两位 Agent 并发修改，可以形成同身份的两个候选修订；如果明确决定把它们作为两条长期独立路线管理，再建立分叉身份。
- 信息不足时保留候选和身份判断的理由，不强行把“相似内容”合并成同一工作。以后纠正身份解释，通过有版本的关联记录表达，不重写已有引用。

“仍然服务同一个用户目标”不足以判成同一工作，因为 A、B、C 可以同时服务那个目标。代码、测试和需求变化范围可以提示人工或 Agent 复核，却不能充当身份真值。该规则仍需真实过程验证，当前不是自动识别算法。

## 2. 创建、修订、分叉可共享登记机制，整合是高阶过程

创建、修订、分叉都可以产生一个明确身份、来源和内容的新版本。这里共享的是**记录新版本的规则**，并不意味着决定身份的过程已经被简化成机械计算。

整合需要额外的语义工作，因此本版把它明确列为高阶组合：

> 选定要取用的成果 → 识别其依赖与冲突 → 形成整合候选 → 记录新版本和关系 → 决定是否选用。

成果边界、语义兼容性和冲突处理由调用者使用工具、LLM 或人工判断。核心检查可核查的条件：来源是否存在、引用是否精确、已声明的必要依赖是否满足、冲突是否被保留、选择是否经过相应权限和规则检查。

核心不能保证调用者没有遗漏隐含依赖。依赖尚未查清时，候选可以保存为待核查，不能因登记成功就宣告兼容。多来源版本仍可以用基本操作保存；但将“整合能力”整体归约为一次生成版本的主张撤回。是否需要独立的整合接口，取决于后续是否出现稳定、不可由现有组合自然表达的协议。

## 3. 关系也版本化，当前配置引用明确的关系集合

本版选择**关系对象有身份和修订版本**。例如 L1 表达“结论 C 基于需求 R 的 v3 和测试 T1”。后来发现测试引用错了，就生成 L2 修正它，保存替代理由和适用范围。L1 仍能用于解释当时的决定。

关系被登记，不意味着它立刻成为所有工作的新依据。当前配置同时引用工作版本和某一版关系集合；采用 L2 后，当前视图才按新关系解释工作。旧配置仍指向原关系集合，历史回看不会被今天的修正悄悄改写。使用关系集合的版本入口，不要求调用者每次逐条填写所有关系。

界面上的“inactive”可以由当前选择计算出来，但不能通过覆盖旧关系来丢失历史。独立的另一组证据可以和旧依据并存；只有明确的修订关系才表达替代，不能把后来出现的关联一律当成覆盖。

工作版本和关系版本共用版本化设施、保留不同类型规则。它增加的成本主要是关系生命周期和选择规则，需要后续检验；不能因为实现设施共用就宣称没有复杂度。

## 4. 选用：允许局部提出变化，整份配置完整生效

调用者可以只提出“把 A2 更新为 A3，B 保持原样”。系统基于指定配置构造完整的新配置，检查后一次登记。它不能只接受请求中方便处理的一半，而悄悄丢掉另一半。

为先把规则说清，本版采用**一份项目配置的串行接纳规则**：候选成果仍然并行保存；只有改变当前项目配置时检查预期旧版本。scope 表示这次调整影响或有权修改的范围，不自动意味着独立事务。

两个 Agent 同时基于 P0 提交安排，第一个成功后，第二个不能覆盖 P1。系统比较原配置 P0、现配置 P1 和第二个请求：

| 情况 | 处理 |
|---|---|
| 更新位置独立，依赖没有变化，合并后仍满足已声明约束 | 可以按确定规则重建候选，重新检查并尝试登记 |
| 修改同一选择为不同值，或者依赖前提已经变化 | 保留双方候选，产生协调事项 |
| 只更新不同位置，却共同违反预算、排他安排等共享约束 | 视为冲突，不能因位置不同自动合并 |
| 语义依赖或兼容性未知 | 保留未决，不当成已证明独立 |

共享约束随项目配置版本化，登记时针对整份新配置检查。外部变化只有进入记录后才能被检查，数据库不能感知尚未报告的现实变化。

协调也不默认全部推给用户：已有明确授权规则的，由程序或指定 Agent 处理并留痕；需要新的语义判断时生成协调候选；只有改变用户意图、重大路线取舍或超出权限，才交给相应决策者。优先级规则须事先声明，不能临时用“最后写入获胜”。这是一种偏保守的初版协议，不声称已经实现高并发。

## 5. 适用性维护怎样由这些操作组成

它是一个组合模式，不增加“万能失效”原语，也不改变研究范围。

**最初：**结论 C1 表示 A7 满足需求 R:v3，测试 T1 明确针对 A7；关系 L1 记录前提、测试和适用范围，配置 P1 选用这些版本。

**要求更新：**生成 R:v4，并提出新的配置。依赖检查发现 L1 的某个必要前提版本改变，记录一项待复核义务，注明触发变化及所用检查规则；和新配置一起登记。C1 与 T1 继续保留为旧条件下的记录，“待复核”不等于“A 已失败”。若能根据明确规则证明改动不影响该前提，则不需要新增复核义务；范围不清楚时保留不确定。

**复核完成：**如果新测试 T2 表明 A7 不满足 R:v4，生成针对新条件的结论 C2，建立相应依据，记录复核结果并更新当前选用。它不推翻“当时针对 R:v3 的测试通过”这个历史事实。若通过，则保存新条件下的支持依据并关闭该复核义务。

StateMem 已有依赖变化触发 needs_recheck 的机制，这个模式不能作为我们的独有增量。我们需要检验的是它与多路线版本、关系修订、执行清单和安排变化能否在同一组操作下协调工作。[StateMem v1，§5，2026；正式发表 venue 待核实](https://arxiv.org/html/2608.19652v1)。

## 6. 近邻比较：比较规则和成本，不靠接口名判断能力

本轮复核后，不能接受“ESAA 只有 append”的描述：它还维护投影、允许动作和任务流转。MAGE 有当前执行路径及分支修订；StateMem 有结构化状态、来源和依赖。因此，显式关系、当前选择、事件登记分别都已有重叠。[ESAA v1，§3，2026](https://arxiv.org/html/2602.23193v1)、[MAGE v1，§3，2026](https://arxiv.org/html/2606.06090v1)。两篇正式发表 venue 本轮仍未核实。

对照应固定相同工作变化，检查各方法怎样表示和更新，再记录需要补哪些约定。**“能把一段话存进去”不等于原生保证其含义；“原文没定义”也不等于理论上不能表达。**十项场景的初步映射和证据范围放在[Agent 说明](primitive-candidates-v0.2-agent-notes.md)，尚未完成代码适配或真实任务重放。

候选的待验证价值是：一套规则能否稳定支持身份延续、并行修订、部分复用、关系修正和当前选用，而不是在每种情形中另加特殊流程。我们还没有证据证明近邻做不到，也不能据此宣称候选已经更通用或更简洁。

## 本版结论与下一步

审阅推动了四个具体决定：身份由有权限的调用者声明；整合明确为高阶组合；关系版本纳入配置；选用接受局部变更请求，但完整配置原子生效。这些是候选设计决定，不是用户已经逐项批准的实现规格。

下一步应在真实材料中逐项检查这些规则，并对近邻做同场景映射。SWE-Milestone 或 SCBench 的阶段规格只能证明需求怎样变化；若缺少实际尝试与决策记录，就不能据此编造“为什么保持身份”或“谁暂停了路线”。内存原型和组合测试是后续检验手段，测试数量由规则和反例决定；本轮没有实现或运行模型实验。

强对照应是认真维护的工作记录、版本引用、决策与执行清单，不限定必须塞进一份 AGENTS.md。简单方案足够时如实记录，它可以改变机制选择；是否改成另一条论文路线，仍需根据整体证据与用户目标判断。
