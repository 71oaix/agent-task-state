# 研究意图：Agent 自主管理软件项目语义状态

## 研究定位

研究对象是**软件项目的语义状态**；研究手段是构建赋予 Agent 自主维护、管理和查询语义状态能力的系统；研究目的是提高 Agent 软件开发的正确率与效率，并探索状态管理机制的可靠性。系统的具体形态与论文贡献尚未确定。

本轮定位依据 2026-11-17 的[论文讨论交接](chatgpt-conversation://6afad74d-dce4-83e9-a1a7-59c848773dfa)及用户在项目会话中的后续补充。前者提供方向演进背景，后者明确职责分工、研究重心和证据边界。聊天中的外部研究描述是待核验线索，不直接作为文献事实。

## 双状态空间与开发闭环

Project State 是事实基础，包括代码、文件、测试、配置和产物。Semantic State 是核心管理对象，包括目标、设计、决策、进度和约束。Human 与 Agent 通过系统提供的工具参与开发及状态维护：实际开发带来新发现和证据，促使语义状态更新；积累的知识再指导后续开发。

语义状态的信息来源包括项目现状、历史演化，以及人和 Agent 直接提出的目标、约束、设计意图和判断。现状说明现在是什么样，历史帮助理解为什么如此；直接声明不必先从历史推导，其来源、权威性与事实支持需分别判断。Task State 从这些持续演化的项目知识中按需产生；这不要求采用 Event Sourcing。

期望形成“开发促进知识积累，知识积累促进开发”的正向循环，将知识构建与维护融入开发活动本身。循环是否有效、维护是否造成额外负担，需要实验判断。Task State 是面向当前任务的状态投影，其生成与持久化方式仍可探索；Human / Agent 视图可服务不同使用者。

工作区作为持续演化的分布式状态系统，是理解异构产物、分散知识与依赖关系的视角。设计倾向是充分利用已有文档、笔记、Issue、测试等工作产物承载的不同知识，让 Agent 管理其归属、关系和有效性，不默认将它们全部复制进另一套集中式记忆结构。具体存储、索引和投影方式仍开放，也不要求采用传统分布式部署架构。

## 设计倾向与职责

系统提供管理能力，由 LLM 自主完成管理活动。LLM 是语义分析与自主维护的主体，系统为这些活动提供可操作的能力与约束。

| LLM 承担的活动 | 系统提供的能力 |
|---|---|
| 判断什么信息值得记录，抽象项目知识 | 状态管理工具、信息组织与持久化 |
| 判断新旧决策的关系 | 关系管理能力 |
| 分析信息是否仍然有效 | 证据与验证机制 |
| 决定何时获取哪些信息 | 状态查询能力 |

这是已明确的设计倾向，尚未落实为工具清单或固定工作流。工具不能仅凭结构检查保证语义判断正确；LLM 能否胜任、需要怎样的提醒、检查或人工辅助，属于研究问题。

## 研究问题与成功判断

“LLM 尚未被充分训练去维护项目语义抽象层”是研究判断，不是已验证事实。当前保留四个问题：

1. 原生 Coding Agent 自主管理项目语义状态的能力如何？
2. 专用管理工具能否改善这种能力？
3. 自主维护产生的语义状态是否可靠，能否避免过时、冲突、错误复用及与项目实际不一致？
4. 改善开发正确率与效率的收益能否抵消记录、更新、验证和查询的维护成本？

有效性与可靠性均需研究。成功证据应能区分状态管理能力、状态质量和实际开发效果，并完整考虑维护成本；若状态更整齐却没有开发收益，不能据此判定系统有效。比较对象、指标、成本口径、失败条件和实验规模待后续协议确定。

| 研究层次 | 当前态度 |
|---|---|
| 有效性（Effectiveness） | 吸收、质疑、验证、改进 |
| 可靠性（Reliability） | 重点探索 |
| 可持续性（Sustainability） | 暂时开放 |
| 连续性（Continuity） | 暂时开放 |

四层用于组织问题，不是必须依次完成的工程阶段。真实接续是候选验证场景，不预先限定整篇研究；也不预先将贡献限定为可靠性模块。

## 项目知识的三个研究环节

构建关注 Agent 能否从开发中提炼出值得留下、证据充分且范围准确的知识。维护关注项目发生变化后，Agent 能否找到受影响的旧判断，保留仍有效的部分，更新或明确标出需要复核的部分。使用关注正确且适用的知识能否在需要时被找到、理解并落实到行动。状态系统提供现状，Agent 决定如何使用。任务通过率本身无法区分这三个环节。

项目知识的形成、变更后的失效与正确知识的使用都是研究场景。逐题揭示是首轮实验选择，让下一项要求在已有代码与知识形成后才出现，便于观察变化如何触发维护。首轮保留会话，把有新需求和丢失前序对话区分开。跨会话接续是独立研究条件，详见[实验协议](../specification/specification.md#首轮实验协议)。

## 学术与工程基础

StateHarness 是学术参考与候选实验基线，用于学习和批判问题定义、状态表达、组织、维护、查询与实验设计。其有效性论证仍需审视；是否正式录用不能代替对原创性和证据质量的判断。

DeepSeek Harness 与其同等重要，是工程参考和潜在机制设计来源。重点分析事实唯一归属（One Home per Fact）、决策替代（Supersession）、生命周期（Lifecycle）、权威性（Authority）、证据验证（Verification）和状态同步（Synchronization）：为什么需要这些机制、解决了什么问题、能否抽象为通用管理能力。此处记录研究线索，不声称本轮已逐项核实 DSH 实现，也不要求直接照搬。

StateHarness 的构建、维护与使用机制提供对照，LongHorizon-Harness 的独立验证与面向目标推进提供设计参照。DSH 可帮助核对实现、验收与证据有效范围在真实工程中如何分离。其他近邻仍需排查，不能只凭单一研究的局限宣称创新空间。

## 技术角色与开放边界

Harness / Tools 提供状态管理能力，Event Sourcing 是候选基础架构思想，Trajectory 辅助分析与评测。Pi 和逐题协议已用于校准，首批样本已冻结。StateSystem（暂名）从状态维护切入，试验同一项状态保留唯一来源、通过链接提供给 Agent 的做法。系统架构、接口、状态表达与查询方式仍保持开放。现阶段证据见[实验记录](../../experiments/chainswe-baseline/state-maintenance-pilot.md)。

五类对象、Change Graph、T12 和离线检查器是已有积累，其证据边界见[已有记录分析](recorded-work-review.md)。不为保留旧成果而限制新研究；最小性可作为候选问题，不预设为主要贡献。

当前不追求通用聊天记忆产品、覆盖所有框架或增加机制以制造差异。付费实验未授权，原始材料留在本地 evidence/；本次意图更新不批准具体架构、实验或实现交接。
